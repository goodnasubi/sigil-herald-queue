## 2. G2 関門 検証記録

ADR 0020 決定 1〜4、および ADR 0066 決定 1〜5 に基づき、各設計決定の適合状況を以下に記録する。

### 2.1 決定 1: 持ち方の選択（独立キューサーバー）
- **形態**: 投入・取得・確認応答（ACK/NACK）を処理する独立デーモンプロセスとして動作。
- **結合度**: 後続部品（メール送信、脅威インテリジェンス配布、動画変換、SNS 通知、イベント処理等）との疎結合性を保ち、専用のライフサイクル管理を提供する。

### 2.2 決定 2: 配送保証とライフサイクル
- **配送保証**: at-least-once（少なくとも1回配送）。重複配送が発生しうる前提でワーカー側の冪等性を想定。
- **リース方式と不可視時間**: `DEQUEUE` 時にジョブを `lease_seconds` の間不可視（invisible）化し、16バイトのリーストークンを払い出し。
- **ACK/NACK**: 有効なトークンでのみ `ACK` による削除を受理。期限切れトークンは `TokenExpired`（エラーコード 23）で拒絶。`NACK` 時は指定遅延（バックオフ）に基づく絶対再配送可能時刻（`visible_at = now + delay_seconds`）を設定。
- **リース期限切れ**: リース期限切れ時に自動的に不可視状態を解除し再配送可能とする。
- **Poison Message 耐性と DLQ**: 再配送ごとに `attempt` を 1 加算。`attempt > max_retries`（既定値 3）で自動的に DLQ（DeadLettered 状態）へ移送し、無限再試行によるキュー滞留を防止。

### 2.3 決定 3: 永続化基盤（sigil-db 核連携）
- **トランザクションと WAL**: ジョブの投入・状態遷移・ACK 消去は、`sigil-db` 核の直列トランザクションを通じて WAL に同期記録。
- **同期保証**: `Enqueued` 応答は WAL 同期（fsync）完了後にのみクライアントへ返却。
- **クラッシュ復旧**: 再起動時に WAL から最新状態を復元。Leased 状態だったジョブはワーカー切断とみなして `attempt` を 1 加算し Ready 状態へ復元（または DLQ 移送）。Delayed 状態のジョブは絶対時刻 `visible_at` により復元。

### 2.4 決定 4: API・プロトコルと DoS 対策・資源上限
- **プロトコル**: 版付き長さ付きバイナリプロトコル（TCP）。
- **フレーム長上限**: 既定 1 MB ＋ 4 KB（1,052,672 バイト）。超過フレームは即座に拒否（`FrameTooLarge`）し接続切断。
- **ペイロード上限**: 既定 1 MB（1,048,576 バイト）。超過ペイロードは型付きエラー（`PayloadTooLarge`）で拒否。
- **同時接続数上限**: サーバー設定 `max_connections`（既定 64）により root タスク数を制限。超過接続はカーネル backlog で待機させクラッシュを防止。
- **I/O タイムアウト**: 1 フレームあたりの読み書き期限 `io_timeout_ms`（既定 10 秒）。低速クライアントをタイムアウトで切断。ロングポーリング（`wait_seconds <= 30`）のみ明示的に延長を許可。
- **待ち受け制限**: 既定の待ち受けはループバック（`127.0.0.1`）。外部接続は明示的な設定と隔離内部ネットワーク運用を前提とする。

### 2.5 ADR 0020 決定 1: 定数時間の検査
- **リーストークン照合**: `herald_queue.sigil` の `owns_lease` において、16 バイトのリーストークン比較に定数時間比較 `ct_eq` を使用。トークン内容の先頭一致度合いによるタイミング攻撃を排除。

### 2.6 ADR 0020 決定 2: ファジング
- **Stage 3 純粋変異ファジング**: 符号化器に対し、正常フレームを変異（ビット反転、切り詰め、延長、境界値、長さ改ざん等）させた 200,000 件の変異フレーム（seed 20261127）を注入し、異常停止（panic）やメモリ破壊がなく、全入力に対して `Ok` または `Err` を返すことを確認（`scripts/test-tcp.sh`）。
- **Stage 3 実ソケット変異ファジング**: 実ソケット経由で 240 件の変異フレームを送信し、サーバーがクラッシュせず後続接続を正常処理することを確認。
- **Stage 4 境界・負荷ファジング**: 境界値（ペイロード境界 1 MiB、フレーム境界 1,052,672 B、遅延秒数 0〜86400、リース秒数 1〜4294967295、再試行回数 0〜4294967295、キュー名長 1〜256）の網羅的検証。

### 2.7 秘密情報の不在確認
- リポジトリ内（コミット履歴、ソースコード、CI 設定）に秘密鍵、API トークン、認証パスワード等の秘密情報が含まれていないことを `git log -p` および走査により確認済み。
- ログ出力においてペイロード生データやトークンを出力しない設計であることを確認。

## 3. 負荷・境界試験の記録（Stage 4）

### 3.1 試験構成
- **環境**: Linux x86_64（Ubuntu 24.04.5 LTS / remote VM）
- **コンパイラ**: Sigil（commit `947815bfa367354dec99bd6308b8931949dec49c`）
- **データベース核**: `sigil-db`（commit `9483e36f08c35bfc62b3beeb008a531887506037`）
- **試験項目**:
  1. ジョブ処理サイクルとスロット再利用試験（逐次 30 回サイクルおよび 10 件バースト時のスロット再利用と有界性検証。1,000 件連続処理は設計目標値）
  2. メモリ枯渇時の振る舞い（※現行ランタイムおよびキュー実装にメモリ上限クォータ・枯渇注入機構が存在しないため未検証と明記）
  3. ディスク枯渇（ENOSPC / `act_fail_space`）および WAL 同期障害時のデータ保全試験
  4. ワーカー突然死・リース期限切れ・Poison Message 耐性・DLQ 移送試験
  5. 期限切れ後の旧ワーカー遅延 ACK に対する `TokenExpired` エラー応答試験
  6. TCP プロトコル DoS 防御試験（過大フレーム、過大ペイロード、同時接続数上限、I/O タイムアウト）

### 3.2 実施結果まとめ

| 試験項目 | 検証シナリオ / 条件 | 期待動作 | 結果 |
|---|---|---|---|
| **ジョブ処理サイクルとスロット再利用** | 連続 30 回の逐次投入・取得・ACK サイクルおよび 10 件のバースト投入・取得・ACK（※1,000 件は設計目標値であり、自動テストの実施条件は 30 件逐次＋10 件バースト） | メモリ・スロットの無制限伸長がなく、既存空きスロットが再利用されスロット配列長が有界（逐次時 1、バースト時 10）に保たれること | 合格 (Pass) |
| **メモリ枯渇時の動作** | メモリ制限の課与・枯渇時の動作検証（メモリクォータまたは OOM 注入） | 上限到達時に新規投入が安全に拒絶され、既存ジョブが破損なく保全されること | **未検証 (Unverified)**（※現行の Sigil ランタイムおよびキューサーバーにメモリ上限クォータやメモリ枯渇注入機構がなく、本テストではスロット再利用のみ検証しておりメモリ枯渇下での既存ジョブ保全は未確立） |
| **ディスク枯渇模擬** | `sigil-db` I/O 関門へ `act_fail_space`（ENOSPC）注入 | `Enqueued` が返らず、WAL 同期前の状態が維持され、再起動後も既存ジョブが破損なく保全されること | 合格 (Pass) |
| **ワーカー突然死** | 貸出中ワーカーの無応答・リース期限超過 | サーバーが自動的に不可視状態を解除し、`attempt` が 1 加算されて再配送されること | 合格 (Pass) |
| **Poison Message 耐性** | `max_retries`（例: 2回）を超える連続クラッシュ・NACK | 再試行上限超過時に自動的に DLQ（`DeadLettered`）へ移送され、通常の `DEQUEUE` 対象から除外されること | 合格 (Pass) |
| **旧ワーカー遅延 ACK** | リース失効・別ワーカー再貸出後の旧トークンでの ACK 送信 | `TokenExpired`（コード 23）で拒絶され、新ワーカーのジョブが二重削除されないこと | 合格 (Pass) |
| **フレーム長上限** | 1,052,672 バイト超（1 MB + 4 KB 超）のフレーム送信 | `FrameTooLarge`（コード 4）で拒絶され接続切断されること | 合格 (Pass) |
| **ペイロード上限** | 1,048,576 バイト超（1 MiB 超）のペイロード投入 | `PayloadTooLarge`（コード 6）で拒絶されること | 合格 (Pass) |
| **同時接続数上限** | 設定接続数（`max_connections = 2`）を超える同時接続 | サーバーがクラッシュせず、空きが生じるまで待機または拒否されること | 合格 (Pass) |
| **低速接続タイムアウト** | `io_timeout_ms` 以内にフレームを完了しないクライアント | タイムアウトで自動切断されること | 合格 (Pass) |
| **既定待ち受け** | `default_config()` の初期値 | `127.0.0.1:7480`（ループバック限定）であること | 合格 (Pass) |

## 4. G3 で所有者へ提示する確認項目

ADR 0020 決定 3 に従い、外部公開を判断する G3 関門において所有者（goodnasubi）へ提示・確認を求める項目を以下に列挙する。

### 1. 単一ノード限定と可用性設計（決定 1、ADR 0066 決定 5）
- **内容**: 初版は単一ノード（単一プロセス・単一 sigil-db インスタンス）限定の設計であり、複数ノード間のレプリケーションや分散合意は持たない。
- **確認事項**: 高可用性（HA）が必要なサービスに導入する場合、インフラ層でのプロセス監視・自動再起動（systemd、コンテナオーケストレータ等）および共有ストレージまたはバックアップ運用を前提とすることの確認。

### 2. メモリ内スロットの保持と再起動時の圧縮運用、およびメモリ枯渇時の動作（P2-1 / Issue #10）
- **内容**: インメモリキューの `slots` 配列は、ACK で空いたスロットを優先再利用する設計。配列長は過去の最大同時保持ジョブ数（ピーク時ジョブ数）で頭打ちとなり、累計処理件数には比例しない。自動テストでは 30 回の逐次処理でスロット長 1、10 件バーストでスロット長 10 に保たれることを確認済み（1,000 件連続処理は設計目標値）。
- **メモリ枯渇時の動作（未検証）**: 現行実装にはプロセスレベルのメモリ制限（メモリクォータ）やメモリ枯渇時の投入拒否機構は存在せず、メモリ枯渇下での既存ジョブ保持動作は未検証である。実運用環境（cgroups 等のコンテナ制限下）で OOM Killer 等によりプロセスが強制終了された場合は、`sigil-db` の WAL から復旧する運用を前提とする。
- **確認事項**: ピーク後のメモリ使用量はプロセス再起動時に有効ジョブ数分へと自動圧縮される。無停止で極端なスパイクを経験した後のメモリ利用特性についての運用上の許容、およびメモリ枯渇時の挙動が未検証であることの了承。

### 3. ディスク枯渇時のフェイルストップ動作（決定 3.1）
- **内容**: ストレージ枯渇（ENOSPC）や WAL 同期失敗が発生した場合、キューサーバーは `Enqueued` を返さずトランザクションを中断し、データ破損を防ぐためにフェイルストップ（新規投入拒絶）する。
- **確認事項**: ディスク使用率のアラート監視および WAL/データ領域の十分な容量確保運用の徹底。

### 4. 外部網接続時の暗号化と認証（決定 4.2）
- **内容**: 本プロトコルは内部網向けの平文バイナリプロトコルであり、トランスポート層での暗号化（TLS）およびクライアント認証機能はプロトコル自体には内蔵されていない。
- **確認事項**: 既定のループバック（`127.0.0.1`）から外部ネットワークへ接続を公開する場合、TLS 終端プロキシ（`sigil-shield-tls` や VPN/mTLS）およびネットワーク分離（VPC、内部専用サブネット）の設置が必須であることの確認。

### 5. 長時間ファジングの実施状況（ADR 0020 G3 確認項目）
- **内容**: G2 では符号化器の 200,000 回変異試験およびソケット経由変異試験を実施済み。
- **対応**: 外部公開を承認する G3 関門の前に、プロトコルパーサーおよびストレージ復元処理について 1 時間以上の長時間ファジングを実施し、所有者へ報告すること。

### 6. 外部公開可否の最終決定
- **結論**: **G2 は外部公開を承認しない**。本検証記録および次期 G3 レビュー結果に基づき、所有者（goodnasubi）が外部公開の可否を最終決定する。
